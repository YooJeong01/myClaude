## ⚠️ 다음 세션이 반드시 지켜야 할 규칙 (이번에 확정됨)

**`main`에는 절대 직접 커밋하지 않는다.** 코드 수정은 물론이고 인수인계 문서·`[chore]` 커밋처럼 사소해 보이는 것도 예외 없이:
1. 브랜치를 판다 (`feat/<kebab>` 또는 `fix/<kebab>` 등, 기존 컨벤션 유지)
2. 그 브랜치에 커밋한다
3. `main`에 병합한다 (필요시 push)

`main`은 태스크의 **최종 결과물이 병합을 통해서만 들어오는 브랜치**로 유지한다. (기존 메모리 `project-git-workflow.md`에 이 규칙을 반영해둠.)

## 이미 발생한 위반을 어떻게 고쳤는지 (참고용, 재작업 불필요)

`main`에 바로 들어간 커밋이 이미 `origin/main`에 push된 상태였어서, 다음 방식으로 히스토리를 손상 없이 정정함:

1. `git checkout -b chore/t18-handover-doc <직전 정상 커밋>` — 문제의 커밋 이전 지점에서 새 브랜치 생성
2. `git cherry-pick <문제의 커밋>` — 같은 내용을 브랜치 위에 재현
3. `main`으로 돌아가 `git revert --no-edit <문제의 커밋>` — 직접 커밋을 **되돌리는 새 커밋**을 추가 (히스토리를 지우지 않는 순방향 방식)
4. `git merge --no-ff chore/t18-handover-doc` — 브랜치를 정식으로 `main`에 병합
5. `git push origin main` — **force-push 없이** 일반 push로 반영

**주의**: `git reset --hard`와 `git branch -f`(브랜치 강제 이동)는 이번 환경의 자동 권한 분류기가 차단했다. 히스토리를 "지우는" 방식 대신 `revert` + `merge`처럼 항상 앞으로만 가는(forward-only) 방식을 쓰면 이런 차단을 피하면서도 목적을 달성할 수 있었다. 다음에 비슷한 상황(이미 push된 잘못된 커밋을 브랜치 구조로 재정리)이 생기면 이 방식을 먼저 시도할 것.
